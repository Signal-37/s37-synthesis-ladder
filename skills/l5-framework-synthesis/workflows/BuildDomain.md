# BuildDomain Workflow

Construct a single L5 Framework domain from a named OA-Principle pairing. This workflow covers the integration act at the domain level — combining a design territory (OA) with its governing principle(s) into a named, sequenced domain with a clear role in the framework's systems logic.

## Step 0: Confirm Domain

Before writing "Why [role]," confirm or inherit the project domain — it determines which systems-logic role names apply.

- **If called from within a SynthesizeFramework session:** inherit the domain confirmed in that workflow's Step 1.
- **If called standalone:** ask the user — brand/design | product/UX | organizational | policy/advocacy | other — then read the matching entry in `DomainScope.md` for the role register (precondition / engine / converter / scale condition per domain).   # domain registry: DomainScope.md | gate: ../ladder-core/config/synthesis-gates.yaml -> gates.domain_scope_confirmation

## When to Use

When you have a named OA-Principle pairing and need to write the domain section. Can be invoked from SynthesizeFramework or called directly when the user hands you a specific pairing to develop.

---

## The Integration Act

Building a domain is not formatting — it is synthesis. The domain is more than the sum of its OA and Principle. The integration produces three things that neither component had separately:

1. **A new name** — not the OA title, not the Principle title, but a name for the integrated territory
2. **A unified strategic task** — not "the OA says X and the Principle says Y" but the single design challenge that both are responding to
3. **A role in the system** — which the OA and Principle individually don't have (an OA is a design territory; a Principle is a standing rule; a domain is a node in an architecture)

---

## Before Writing: Establish the Pairing

Before writing a single word, confirm that the pairing is genuine:

1. Read the OA's "What's in scope" items as decision types
2. Apply the Principle's test question to each scope item: does it yield a directional answer?
3. If yes across most scope items → genuine pairing
4. If the Principle's test question only applies to some scope items → check whether a second governing Principle is needed for the remainder

**If two Principles are needed:**
Name both as governing Principles. Structure "What this domain governs" by phase or dimension — one section per Principle's territory. Write "The strategic task" to integrate both.

**If no Principle fits well:**
Do not force a pairing. Return to the L4 Principle set and check whether a governing Principle was missed. If genuinely absent, flag this for the user before proceeding.

---

## Writing Order

Write the content first and the name last (the researcher, 2026-11-06 for L2 and L3; extended to L5 2026-11-07). A name chosen first and defended afterwards tends to carry the argument in a clever word. All text in this domain follows `FrameworkFormat.md` → Plain Writing (statements and names).

**1. Write "The strategic task."** The synthesis argument — what must be done in this domain, and why. This section draws from both the OA ("What this designs") and the Principle ("How every decision within it should be made") and states them as a unified challenge.

Structure: name the structural problem → state the task as an organizational design challenge → name what happens if the task is not addressed.

Do not list programs. Do not repeat the OA's scope items. Argue the necessity of this domain in 2–4 sentences.

**2. Write "What this domain governs."** The specific contents — programs, systems, frameworks, toolkits, design tasks. Pull from the OA's scope and enrich with research evidence.

For each item, ask: what specific participant, finding, or historical precedent makes this item non-negotiable? Name it. "Dealer narrative toolkit" is a scope item. "Dealer narrative toolkit — Kian Karl built his own because Meridian didn't provide one; the toolkit gives the next dealer the same credibility without the improvisation" is a domain content item.

Organize by phase or dimension if the domain has two governing Principles. Label each phase.

**3. Write "Why [role]."** The sequencing argument. Name the domain's structural role using the project domain's role register from `DomainScope.md` (precondition / engine / converter / scale condition for brand/design; the equivalent names for product/UX, organizational, or policy/advocacy — matching the register the OA used at L4) and argue for it specifically.

Structure: "[This domain] is [role] because [specific argument]. Without it, [specific failure]. With it, [specific system outcome]."

The argument must be specific to this domain in this framework — not generic claims about why "identity matters" but why *this identity domain* is the precondition for *these specific other domains* in *this framework*.

**4. Name the domain.** Now state in 1–2 plain words what the domain covers, from what steps 1–3 wrote.

Draft 3 candidates. Test each:
- Is it short? (1–2 words)
- Could a reader with no project context say what falls inside this domain from the name alone, without it being explained?
- Is it literal: no figure of speech, coined term or clever contrast?
- Is it distinct from the other domain names?

**5. Write the one-line descriptor.** A plain statement of what the domain is for, in the reader's ordinary words. It is not a slogan, a command or a pair of imperatives. "What the brand stands for, and where buyers see it", not "Name what you stand for. Show where it lives."

**6. Write the header block.** Domain name, descriptor, OA reference, Principle reference(s).

## Domain Name Construction — Patterns

Strong domain names from practice:

| Pattern | Example | When to use |
|---------|---------|-------------|
| **Abstract noun** | Identity / Growth / Experience / Access | When the territory is broad and the name creates a container for multiple programs |
| **Action noun** | Activation / Design / Service | When the territory is defined by a type of activity |
| **Relational noun** | Community / Relationship / Belonging | When the territory is defined by its human subject |
| **Strategic noun** | Foundation / Architecture / System | When the domain is primarily organizational capability |

Avoid:
- Figures of speech and coined terms: "The Flywheel", "Ground Truth" — a cold reader cannot say what they cover
- Technical program names: "Community-Led Growth Architecture" is an OA title, not a domain name
- Abstract strategy language: "Value Creation" / "Competitive Differentiation"
- Names that describe a function rather than a territory: "Marketing" / "Sales" / "Operations"

---

## Descriptor Construction — Patterns

The one-line descriptor is a plain statement of what the domain is for. It should be readable as a standalone sentence by a reader with no project context. Rules: `FrameworkFormat.md` → Plain Writing (statements and names).

| Fault | Before | After |
|-------|--------|-------|
| Pair of imperatives | "Name what you stand for. Show where it lives." | "What the brand stands for, and where buyers see it." |
| Command with no object a reader can see | "Design the moments that matter." | "The points in a purchase where buyers decide, and how the brand handles them." |
| Figure of speech | "Invest where conviction forms." | "Spend where riders decide to buy, which is on rides with people they know." |
| Categorical reframe | "Welcome as a brand act." | "How new owners are welcomed, treated as part of the brand's work." |

A descriptor may draw on the governing Principle, but it states what the domain covers. It does not restate the Principle as a slogan.

---

## Domain Quality Check

Before finalizing:
- [ ] Domain name is 1–2 words, plain, understood on first read without explanation, not the OA title, not the Principle title
- [ ] Descriptor is one plain sentence saying what the domain is for — not a slogan
- [ ] Name and descriptor were written after the domain content
- [ ] All text meets `FrameworkFormat.md` → Plain Writing (statements and names)
- [ ] OA and Principle references are correctly cited
- [ ] "The strategic task" names the structural problem AND the design challenge as a unified statement
- [ ] "The strategic task" does not list programs — it argues necessity
- [ ] "What this domain governs" includes specific participant names, quotes, or historical precedents
- [ ] "What this domain governs" is organized by phase or dimension if two governing Principles apply
- [ ] "Why [role]" names the specific structural role AND what breaks if the domain is absent
- [ ] "Why [role]" is specific to this domain in this framework — not generic
