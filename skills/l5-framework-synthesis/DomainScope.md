# Domain Scope Reference

Defines the domain-coupled vocabulary for the L5 Framework. The integration machinery in `FrameworkFormat.md` — the pairing logic (OA + Principle → Domain), domain naming discipline, the feedback-loop requirement, the governing-condition check, the three practical uses, The Refusal — is universal. This file parameterizes only two layers: the **systems-logic role register** (the structural roles domains play in the architecture) and the **closing-question / framework-name register** (whether the framework answers a "brand," "product," "organizational," or "policy" question).

The systems-logic roles here are the OA relationship-map roles (`l4-opportunity-area-synthesis/DomainScope.md`) elevated to the domain level — keep them consistent: a domain's role in the L5 architecture should use the same register as its OA used at L4.

Confirm the domain at the start of SynthesizeFramework (Step 1). The L4 Opportunity Area and Principle files both carry a `domain:` field — inherit it (they will agree) and confirm rather than re-asking. Carry the domain forward into the L5 framework and visual frontmatter.

The five domains match the rest of the ladder exactly.

> Framework names in every register below must be understood on first read by a reader with no project context: `FrameworkFormat.md` → Plain Writing (statements and names).

> The role names below are the default register per domain; the framework may name a fifth role or rename one where the evidence demands it (the format already allows this). The point is to start from the domain's register rather than defaulting to the brand/growth one.

---

## brand/design

**Systems-logic roles:** Precondition · Growth engine · Converter · Scale condition

**Closing-question / framework-name register:** A *brand* (or strategic) question — "How does [brand] activate the equity it has built…?" Framework names like "Brand Equity Activation Framework."

---

## product/UX

**Systems-logic roles:** Precondition (foundational capability) · Adoption engine (primary activation mechanism) · Retention converter (turns adoption into sustained use) · Scale condition

**Closing-question / framework-name register:** A *product* question — "How does [product] turn first use into durable, expanding value…?" Framework names like "Product Adoption Architecture."

---

## organizational

**Systems-logic roles:** Precondition (shared frame all domains require) · Primary mechanism (the main change lever) · Sustaining mechanism (what makes the change stick) · Scale condition (what spreads it across the org)

**Closing-question / framework-name register:** An *organizational* question — "How does [organization] change how it works so the change holds…?" Framework names like "Operating Model Framework."

---

## policy/advocacy

**Systems-logic roles:** Precondition (enabling condition) · Primary lever (the main intervention) · Sustaining mechanism (what maintains the outcome) · Reach condition (what extends it to those currently excluded)

**Closing-question / framework-name register:** A *policy* question — "How does [body] deliver the outcome to those it currently fails to reach…?" Framework names like "Access & Delivery Framework."

---

## other

**Systems-logic roles:** Use the four structural roles that fit the evidence — typically an enabling precondition, a primary mechanism, a sustaining/converting mechanism, and a scale/reach condition. Name them in the system's own terms.

**Closing-question / framework-name register:** Name the question in the terms of whoever owns the system — the framework answers their question, in their vocabulary.
