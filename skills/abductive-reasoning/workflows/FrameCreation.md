# FrameCreation Workflow

Generate a new frame — a working principle borrowed from another domain — for a problem where only the desired outcome (VALUE) is known and conventional approaches have failed or stalled. This is the operative workflow for **abduction-2**: the case where neither the solution (WHAT) nor the working principle (HOW) is given, and both must be invented simultaneously.

**The logical structure this workflow addresses:**

```
Known: VALUE only (the desired outcome, experience, or impact)
Unknown: WHAT (the solution) + HOW (the working principle)
Method: Find a frame — a provisional HOW from another domain — that makes the WHAT searchable
```

A frame is not a solution. It is a lens: a conditional working principle that, when applied to the situation, makes a whole class of solutions visible that were invisible before. *If we approach this situation as if it were <X domain>, then <working principle Y> applies, and solutions of type <Z> become available.*

## When to Use

- KnowledgeFunnelMapping has placed a problem in Mystery territory with a VALUE-only specification
- A problem has been attempted multiple times with different solutions and keeps failing in the same way — the frame, not the solutions, may be the problem
- ObservationToHypothesis Step 0 (mode selection) routes to the prospective path
- Synthesis is stalled because no framing makes the evidence cohere into a design direction

**Not for:** Problems where a working principle already exists and the task is finding the right instantiation (that is abduction-1 — use ObservationToHypothesis directly). If you can already name the *type* of solution needed, you are in abduction-1 territory.

**If escalating from a mid-ladder synthesis stall** (rather than a standalone reframing engagement): Steps 1 and 3 draw on the client's prior solution history and the existing L0/L1 field data — they do not require new fieldwork. If neither exists, this workflow is not the right escalation; use ObservationToHypothesis on the stalled material instead. The selected frame re-enters the ladder as the organizing hypothesis for the level transition you escalated from.

> **Data gate:** Steps 1 and 3 operate on user-supplied material — the problem owner's actual intervention history (Step 1) and real stakeholder practices from existing fieldwork or the user's direct knowledge (Step 3). If neither has been provided, halt and ask; a genealogy or practice map invented to feed the workflow produces frame theater. Adjacent-domain material contributed from training knowledge in Steps 4–6 is governed by the anti-fabrication rules at those steps.

---

## Scope

This workflow covers **Steps 1–7** of Dorst's nine-step Frame Creation process (Archaeology through Futures). These are the design-based abductive synthesis steps. *(The 1–7 / 8–9 boundary is this skill's scope decision, not Dorst's; he groups the steps as groundwork, 1–4, and exploration, 5–9.)*

Steps 8–9 (Transformation and Integration) are organizational change management — determining whether the organization can make the transition to operating inside the new frame, and embedding it in practice. These steps require client-side organizational authority and are outside the scope of design synthesis work. They are named here for completeness; a separate implementation brief is the appropriate vehicle.

---

## Process

### Step 1: Archaeology — Map the Problem's History

**Purpose:** Understand what has been tried before and what frame each previous attempt was operating under. The pattern of failures reveals the assumptive structure keeping the problem locked.

Investigate and document:

```
## Problem Genealogy

**Problem as stated:** <How the problem is currently framed by the owner>

**Previous intervention <N>:**
- What was tried: <Specific approach or solution>
- Implicit frame: <What working principle this approach assumed — even if never stated>
- Why it failed or fell short: <Specific failure mode, not generic "didn't work">

**The pattern across failures:**
<What is common across the failed interventions? Are they all variants of the same underlying approach?
If yes — the current frame is likely the problem, not the execution of solutions within it.>
```

**Diagnostic signal:** If every previous attempt is a variation on the same solution class, the problem is framed in a way that makes only that solution class visible. The archaeology has found the lock; the paradox step names it.

**Frame-naming guard:** State each implicit frame as a *working principle* ("this approach assumed trust is built by proximity"), not a solution restatement ("the frame was to add more branches"). If your frame statement names a thing that was built rather than a principle that was assumed, you have restated the solution — dig for the assumption underneath it.

---

### Step 2: Paradox — Name the Deadlock

**Purpose:** Articulate the core structural tension that makes the problem unsolvable inside its current frame. The paradox is not a hard problem — it is a logical or pragmatic deadlock where honoring one true thing makes it impossible to honor another true thing simultaneously.

A design paradox has this structure (after Dorst 2015, p. 51): two or more statements, each true on its own terms, that cannot be combined for logical or pragmatic reasons. More solutions of the current type will not resolve it — the tension is in the frame, not in the execution.

```
## The Paradox

**True statement A:** <Something the problem owner cannot give up — a genuine requirement>
**True statement B:** <Something equally true that conflicts with A>

**The deadlock:** Honoring A makes B impossible because <specific mechanism>.
Honoring B makes A impossible because <specific mechanism>.

**What this rules out:** Any solution that operates inside the current frame will be forced to
choose between A and B. No amount of better execution within the current frame resolves this.

**What a successful frame must accomplish:** It must dissolve this tension — not by eliminating
A or B, but by finding a different organizing logic in which A and B are no longer in conflict.
```

**Check:** If the paradox statement could be "solved" by a better version of an existing approach, it is not a genuine paradox — it is a hard problem. A genuine paradox requires a different frame, not a better execution.

---

### Step 3: Context — Map Current Stakeholder Practices

**Purpose:** Understand what key people actually *do* in and around the problem situation — their routines, their workarounds, the informal solutions they have already invented. This is ethnographic, not analytical: the question is behavior, not stated preference.

For each key stakeholder directly involved with the problem:

```
## Stakeholder Practice Map

**Stakeholder:** <Role or description>
- **What they actually do:** <Specific practices, routines, behaviors — observed or reported>
- **What matters to them:** <Values implicit in their behavior — not what they say matters>
- **Workarounds they have developed:** <Informal solutions they have invented to cope>
- **Where they experience friction:** <Where current arrangements fail them specifically>
```

**Note:** Context is focused on *current, known* stakeholders directly engaged with the problem. The next step (Field) widens the arena. Do not try to map the full ecosystem here — that produces noise. Context is close-in observation; Field is deliberate widening.

---

### Step 4: Field — Widen the Arena

**Purpose:** Radically expand who and what is relevant. Move from the immediate problem owner's world to the full intellectual, economic, cultural, and social space surrounding the problem. This step is the raw material from which themes emerge.

Expand across four dimensions:

```
## Field Map

**Who else could be involved?**
<Stakeholders not currently engaged — adjacent communities, affected populations, potential partners,
domain experts from outside the immediate field. Why might they be relevant?>

**What adjacent domains deal with structurally similar situations?**
<Other fields, industries, or practices that encounter the same structural tension — different
surface form, same underlying dynamic. List at least three.>

**What power dynamics and institutional structures shape this space?**
<Who controls access, resources, permissions? What organizational or policy structures constrain action?>

**What value systems are present that are not currently represented?**
<Whose values or interests are absent from the current problem framing?
What would the problem look like from those perspectives?>
```

**The adjacent domains list** in "structurally similar situations" is the most important output of this step — it feeds frame generation in Step 6. Be generous. The correct source domain for the frame is rarely obvious at this stage.

> **Anti-fabrication rule:** Adjacent domains and their practices may come from training knowledge — that is this step's legitimate function — but do not invent named organizations, case outcomes, statistics, or specific programs as evidence that a domain "solved" the dynamic. A domain claim that depends on a specific named case carries `[model knowledge — verify]`.

---

### Step 5: Themes — Identify Deep Cross-Stakeholder Patterns

**Purpose:** Synthesize the Field map into structural themes — deep, cross-cutting patterns of need, motivation, value, or social dynamic that are relevant across multiple stakeholders and contexts. Themes are descriptive; they characterize what is structurally true about the problem field.

**The critical distinction:**

| Themes | Frames |
|---|---|
| Descriptive — what is true across the field | Normative — how to act in response to what is true |
| Emerge from the field data | Are imported from adjacent domains |
| Describe human/social/organizational dynamics | Propose a working principle from elsewhere |
| Output of this step | Output of the next step |

A theme sounds like: *"People in this situation value feeling acknowledged over receiving material assistance"* or *"Every transaction in this arena is structured by mistrust even when both parties nominally want collaboration."*

A frame sounds like: *"IF we treat this situation as a hospitality problem rather than a security problem, THEN <working principle Y> applies..."*

If what you have written sounds like a proposed solution or an organizing strategy, it is probably a frame candidate, not a theme. Move it to Step 6.

Generate 3–7 themes. For each:

```
## Theme <N>: <Short evocative name>

**Pattern:** <What is structurally true across the Field — stated as a cross-stakeholder behavioral
or social dynamic, not a solution direction>

**Evidence from the Field:** <Which stakeholders, observations, or adjacent domain analogues
support this pattern>

**Why it matters for the paradox:** <How this theme relates to the core tension identified in Step 2>
```

---

### Step 6: Frames — Generate Candidate Working Principles

**Purpose:** For each theme, identify an adjacent domain where that pattern already has a well-developed organizing logic, and import that logic as a provisional working principle — a frame. This is the core abductive operation.

**The operative question for each theme:**
*In what other domain, practice, or field does this pattern already have an established, productive working principle?*

**Frame construction template** (extends Dorst's formulation, "If the problem situation is approached as if it is … , then …", 2015, p. 78):

```
IF we approach <this situation> AS IF it were <domain/practice X>,
THEN <working principle Y from that domain> applies,
WHICH means solutions of type <Z> become available —
AND the paradox <A vs. B> dissolves because <specific mechanism>.
```

The frame is a hypothesis. It cannot be proven from the themes — it is abducted from them. The test is not logical derivation but productive fit: does this frame generate solutions, dissolve the paradox, and create value across stakeholders?

**Domain borrowing technique:**

For each theme, work through this sequence:

1. **Name the structural dynamic** — strip the theme of its surface content and state the pure dynamic. "People mistrust intermediaries between them and their goals" is a structural dynamic. "Customers don't trust banks" is a surface observation.

2. **Ask: in what domains has this dynamic been successfully organized?** List at least three candidate source domains, drawn from the Field map's adjacent domains list. Do not filter at this stage — generative before evaluative.

3. **For each candidate domain: name the working principle** that makes this dynamic productive or manageable in that domain. What do practitioners in that domain *do* that addresses this dynamic?

4. **Construct the IF/THEN frame formulation** for the most promising working principles.

5. **Test against the paradox**: Does operating inside this frame dissolve the tension between A and B, or does it just relocate it?

**Generate 2–5 candidate frames.** Fewer than two gives no comparative basis. More than five disperses attention across the futures step.

**Frame quality criteria:**

| Criterion | Question | Good frame | Weak frame |
|---|---|---|---|
| **Fruitfulness** | Does it open multiple solution directions? | Generates a class of solutions | Points to one solution |
| **Paradox dissolution** | Does it dissolve the Step 2 tension? | A and B are no longer in conflict inside this frame | The tension re-emerges in new form |
| **Stakeholder coherence** | Does it create value for multiple field actors? | Multiple stakeholders gain something | Only the problem owner gains |
| **Transferability** | Can the working principle actually move from source to target domain? | The mechanism is legible in the new context | The analogy holds at the surface but the mechanism doesn't transfer |
| **Novelty** | Is this genuinely different from the current frame? | Different organizing logic | Relabeling of the current approach |
| **Exclusion** | What solution directions does it rule OUT? | Names what it forecloses — the frame constrains real choices | Excludes nothing — a generativity engine, not a decision filter |

**Rejection gate:** A frame rated weak on **Novelty** or **Transferability**, or that can name nothing it excludes, is discarded here — not advanced to Step 7. A relabeling, a surface analogy, or an excludes-nothing frame is not a candidate frame. *(The Exclusion criterion and this gate are this ladder's additions, 2026-07-11 — not part of Dorst's published criteria; added so the frame functions as a decision filter, per the l4-design-principle-synthesis "what it prevents" discipline.)*

---

### Step 7: Futures — Develop and Evaluate Frame Scenarios

**Purpose:** For each candidate frame, develop a scenario — a narrative of what the problem situation would look like if the frame were adopted and its working principle put into practice. Evaluate each frame against three criteria to determine which to advance.

This is not solution design. The scenario operates at the frame level: what would change, who would do what differently, what new possibilities would become visible? Specificity should be sufficient to evaluate the frame, not sufficient to specify a deliverable.

> **Anti-fabrication rule:** Scenarios are explicitly hypothetical — they describe what *would* change under the frame. Keep them at that register: do not invent stakeholder quotes, adoption statistics, or named precedents as if observed. Scenario details added for vividness carry `(illustrative framing)`.

**Scenario structure for each frame:**

```
## Frame <N> Scenario: <Frame name>

**Frame:** IF <situation> AS IF <domain X>, THEN <working principle Y>

**If this frame were operative:**
- <Stakeholder A> would <do differently / have access to / experience...>
- <Stakeholder B> would <...>
- <What new relationships, roles, or resources would emerge>
- <What solutions of type Z become available that were invisible before>

**Specific solution directions this frame generates:**
1. <Direction 1 — stated at intervention-type level, not deliverable level>
2. <Direction 2>
3. <Direction 3 — there should be at least three; if not, the frame is abduction-1 not abduction-2>
```

**Evaluate each frame against three criteria drawn from Dorst's Futures step** (2015, pp. 78–79: whether the frame puts the work "on the right track," its "fruitfulness," and a value proposition for all parties involved; the numbered wording below is this skill's):

```
## Frame Evaluation

**Frame <N>:** <Name>

1. Directional validity: Does this scenario point toward the desired VALUE?
   Does it address the paradox identified in Step 2, or dissolve it?
   <Pass / Partial / Fail — with specific reason>

2. Fruitfulness: Does the frame generate at least three genuinely different solution directions?
   Or does it converge on a single solution type?
   <Pass / Partial / Fail — list the solution directions; if only one, flag as abduction-1>

3. Stakeholder value: Does the scenario create genuine value for each significant stakeholder
   in the Field — not just the problem owner?
   <Pass / Partial / Fail — state what each key stakeholder gains or loses under this frame>

4. Exclusion (added by this ladder — not drawn from Dorst): What does this frame rule out?
   Name at least one solution direction or approach the frame forecloses.
   <Pass / Partial / Fail — a frame that excludes nothing cannot function as a decision filter>

**Overall assessment:** <Advance / Revise / Discard — with specific reason>
```

**Frame selection output:**

```
## Selected Frame(s)

**Primary frame:** <Name and IF/THEN formulation>
**Rationale:** <Why this frame scored best across the three criteria>
**How it dissolves the paradox:** <Specific mechanism — how A and B are no longer in conflict>
**Solution territory it opens:** <The class of solutions now available>

**Runner-up frame (if any):** <Name — keep available for subsequent design phases or if primary frame encounters resistance>

**Discarded frames:** <List with one-line reason for each — not pursuing, not destroying>

**Status label (required on every presented output):** [HYPOTHESIS — selected frame, a provisional bet; requires testing before presenting as strategy]
```

---

## Output

A Frame Creation document containing:
1. Problem genealogy (Step 1)
2. Paradox statement (Step 2)
3. Stakeholder practice map (Step 3)
4. Field map with adjacent domains list (Step 4)
5. 3–7 themes (Step 5)
6. 2–5 candidate frame formulations (Step 6)
7. Scenario evaluations and selected frame(s) (Step 7)

**What happens next:**

The selected frame provisionally fixes the HOW. This makes the problem an abduction-1 challenge: the working principle is now known, and the task is finding the right WHAT. Route to **ObservationToHypothesis** (which will now operate in prospective mode — the frame is the organizing hypothesis, and the workflow generates and evaluates WHAT candidates) or directly to synthesis research designed to test and elaborate the frame. If you escalated here from a ladder stall, the selected frame is the organizing hypothesis for the level transition you came from — re-enter that rung with it.

**Labeling requirement:** All outputs from this workflow are hypotheses. The selected frame is a provisional bet — the best current explanation of how to make progress on this problem. It is not a strategy until tested. Every frame output must be clearly labeled `[HYPOTHESIS — selected frame, a provisional bet; requires testing before presenting as strategy]` when presented to stakeholders.

## Known Limitations

Frame generation (Step 6) is the expertise-dependent operation. The leap from themes to frames is not rule-governed — it requires genuine cross-domain knowledge and the willingness to make an unproven bet. This workflow scaffolds the operation but cannot substitute for the background knowledge that makes a genuinely novel frame possible. If all candidate frames feel like restatements of the current approach in different vocabulary, the domain search in Step 4 (Field) needs to widen further.

Frame failures in implementation (post-Step 7) most commonly occur when: (a) the problem owner cannot detach from the original frame to evaluate new ones; (b) the new frame cannot be mapped onto existing organizational structures; (c) the frame is intellectually coherent but organizationally threatening. These are Steps 8–9 concerns — outside this workflow's scope — but worth naming explicitly when presenting frame candidates to clients. *(Lee 2020)*
